# Service Management App E2E Test Plan

## Scope
Chromium tests run against the production build at the DataMiner public-app base path. No live system or credentials are used: DataMiner authentication is mocked at the documented `IsConnectionAlive` boundary, and Service Management data reads and writes are mocked at the UDAPI boundary. The app calls `SLC_SM_UDAPI_ServiceManagement` through `ExecuteAutomationScriptWithOutput`; its routes cover orders, services, categories, specifications, configurations, items, related orders, monitoring services, and service scripts.

The direct GQI query used by the app is the service-organization lookup; it is mocked at the query-session boundary (`/API/v1/Internal.asmx/OpenQuerySession`, `GetNextQuerySessionPage`, `CloseQuerySession`). Document Hub logo choices are returned by the read-only `SLC_SM_AS_GetDocumentHubLogos` Automation script and are mocked through `ExecuteAutomationScriptWithOutput`. The GQI mock validates the request (connection from the `DMAConnection` cookie and the deployed data source descriptor) and exercises paging. UDAPI mocks return enriched records but do not enforce every controller state rule. Configuration scenarios mock the UDAPI specification list, `GET serviceSpecification/{id}` (service items), and service/specification configuration GET/PUT routes. The service-item-specific interactive script is mocked separately at the IAS WebSocket boundary.

## Exclusions
The IAS WebSocket mock covers the `Launch Interactive Subscript` flow for a service item's own script (for example, an SRM Booking Manager wizard). A live DMA check is still required to confirm the real dialog round trip, completion result, and permissions. The dev mock (`npm run dev:mock`) has no WebSocket endpoint, so the IAS dialog reports a connection error there.

Realtime GQI updates remain out of scope. The only direct GQI data source left in the app is `SLC_SM_GQIDS_Get Service Organizations` for organization selection. Document Hub logo selection uses the read-only `SLC_SM_AS_GetDocumentHubLogos` Automation script. There is no GQI/script fallback for Service Management data operations.

All other Service Management reads and writes go through `SLC_SM_UDAPI_ServiceManagement` (Run entry point, raw `Request` parameter) with the user's session. Orders use `serviceOrder` and its item, transition, configuration, and initialization routes. Services use `service`, `monitoringService`, and the related-order, duplicate, transition, item, configuration, and script routes. Categories and specifications use `serviceCategory` and `serviceSpecification`; specification items are read through `GET serviceSpecification/{id}?fields=ServiceItems` and changed through the specification item routes. Configuration reads and writes use the service, service-order-item, and specification configuration GET/PUT routes. The service-item-specific interactive script remains an IAS workflow; it does not handle Service Management CRUD.

The service controller currently requires public IDs matching `SERVICE-<number>`; the UI enforces this for new services, and nonconforming existing IDs cannot be addressed by these routes. No legacy fallback remains for them, so they must be normalized or the controller adjusted before deployment. Re-run `SLC_SM_Setup_UDAPI` to register route changes. The compatibility target is DataMiner 10.6.8 Feature / 10.7.0 Main; category/specification PATCH also requires PATCH User-Defined API support in the target runtime. The API enforces order-state and relationship rules (including item-add restrictions outside New/Acknowledged and item edit/delete restrictions for non-New items), returning conflicts for invalid mutations. E2E tests use mocks; live DMA verification is still required for deployment, runtime-version support, permissions, and actual DOM/API behavior.

## Live preview
`npm run dev` uses live same-origin DataMiner requests. For local live-DMA development, set `VITE_DATAMINER_ORIGIN` to the DMA base URL so Vite proxies `/API` (including the `/API/v1/WebSocket.ashx` WebSocket used by the IAS dialog) and `/auth`. `npm run dev:mock` explicitly enables the sample data from `dev/mockDataMiner.js` (dev server only, never part of `vite build`).
